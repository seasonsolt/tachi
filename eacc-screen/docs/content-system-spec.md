# Content System Spec — e-acc.ai Phase 1

## Phase-1 guardrails
- `e-acc.ai` is the only active public domain for this launch window.
- `e-accs.com` stays deferred until the main site proves traction.
- Workflow/tutorial pages are the primary asset; comparison pages exist to support workflow intent, not replace it.
- The legacy ritual experience stays reachable on `/ritual` (or an implementation-equivalent lab route), but it no longer owns the root homepage.
- Ads are supplemental revenue. Every monetized page should also prepare either an affiliate/referral CTA, a newsletter capture, or both.

## Frontmatter contract
Every content source file should expose these required fields so route generation, sitemap creation, and revenue instrumentation can stay data-driven.

| Field | Required | Notes |
| --- | --- | --- |
| `slug` | yes | Route-safe unique identifier |
| `title` | yes | Public page title |
| `description` | yes | SEO/social summary used by build and manifest output |
| `cluster` | yes | Hub/topic owner or `core-entry` / `ritual-lab` |
| `intent` | yes | `homepage`, `hub`, `workflow`, `comparison`, or `lab` |
| `ctaType` | yes | `newsletter`, `affiliate`, `internal-lab`, or another first-party CTA family |
| `updatedAt` | yes | ISO date for freshness and audits |
| `monetizationMode` | yes | Ordered list of channels. Single-line comma lists and YAML bullet lists are both accepted by the parser. |

Recommended optional fields: `primaryRoute`, `summary`, `featuredWorkflowSlugs`, `relatedHubSlugs`, `relatedComparisonSlugs`, `status`, `estimatedReadMinutes`, `owner`.

## Route families
| Route family | Purpose | Rendering expectation |
| --- | --- | --- |
| `/` | Content homepage for AI builder playbooks | Pre-rendered HTML |
| `/hub/:slug` | Cluster page that groups workflows and support comparisons | Pre-rendered HTML |
| `/workflow/:slug` | Primary tutorial/workflow page | Pre-rendered HTML |
| `/compare/:slug` | Support comparison/review page tied to one or more workflows | Pre-rendered HTML |
| `/ritual` | Preserved immersive ritual screen | SPA/lab route allowed |

## Template specs

### Homepage template
Purpose: explain what `e-acc.ai` helps a builder do in plain language.

Required modules:
1. Hero promise for solo AI builders.
2. Cluster chooser linking to hub pages.
3. Featured workflows with concrete outcomes.
4. One support comparison highlight.
5. Newsletter or email capture CTA.
6. Link to the preserved ritual lab.

### Hub template
Purpose: map one cluster to repeatable outcomes and route readers deeper.

Required modules:
1. Cluster framing and audience.
2. Workflow ladder (`start here`, `next step`, `advanced`).
3. Related comparison links.
4. Newsletter/email capture block.
5. Optional ad slot below the first workflow group.

### Workflow template
Purpose: be the primary SEO + monetization surface.

Required modules:
1. Problem / desired outcome.
2. Tool stack.
3. Prerequisites.
4. Build steps in fixed order.
5. Failure modes and guardrails.
6. Alternatives or when not to use the stack.
7. Primary CTA block (affiliate/referral or newsletter).
8. Secondary monetization placement (ad slot or related offer).
9. Internal links to exactly one hub and at least one comparison/support page.

### Comparison template
Purpose: support BOFU intent generated by workflow pages.

Required modules:
1. Recommendation snapshot.
2. Who each tool is for.
3. Where it fits inside a workflow.
4. Trade-offs / pricing caveats.
5. CTA block that preserves editorial trust.
6. Links back to the most relevant workflows.

### Ritual / lab template
Purpose: preserve the brand's ambient ritual DNA without occupying the main SEO entrypoint.

Required modules:
1. Short explanation that this is the original immersive experience.
2. Clear return path to the content homepage.
3. Optional CTA back into the newsletter or featured workflow set.

Implementation note:
- `/ritual` is served by the preserved client SPA shell.
- `content/pages/ritual-lab.md` is supporting editorial copy, not the canonical runtime artifact.
- Ritual traffic is reported separately under preserved route metrics rather than being mixed into content-route publishing totals.

## Monetization rules
- Ads cannot be the only monetization element on any workflow or comparison page.
- Workflow pages should default to `affiliate, newsletter, ads` or `newsletter, ads`.
- Comparison pages should default to `affiliate, ads, newsletter` with a trust note explaining recommendation criteria.
- Homepage and hub pages should bias toward email capture first, ads second.
- Event instrumentation should be able to attribute `page_view`, `cta_click`, `newsletter_signup`, and `revenue_recorded` by slug.

## Internal-linking rules
- Every workflow links back to one hub and forward to one comparison page.
- Every comparison links back to at least two workflows when available.
- Homepage highlights both launch hubs and the ritual lab.
- The launch batch must provide at least: 1 home, 2 hubs, 3 workflows, 1 comparison, and 1 ritual/lab page.

## Evidence hooks for implementation + verification
1. The route manifest must match `content/launch-batch.json` plus markdown frontmatter exactly for every non-ritual launch route.
2. Non-JS crawlability proof should be collected for `/`, one `/hub/:slug`, one `/workflow/:slug`, and one `/compare/:slug`.
3. The weekly revenue ledger must be able to answer revenue mix and progress toward the `$50/month` north-star.
4. `e-accs.com` should appear only in deferred/backlog notes, never as an active launch route.
